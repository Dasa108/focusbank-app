What is an Android App?

An Android app is a sandboxed package (.apk or .aab) running inside the Android Linux runtime (ART). Each app runs under its own Linux User ID (UID), completely isolated from other apps unless granted explicit OS permissions.

Analogy: Think of the phone as a secure office tower. Each app is a locked private office. To look out into the hallway (other apps), FocusBank must request an official security badge (Accessibility permission).
2

The Conductor: Gradle

Gradle is the automated build robot. When you run ./gradlew assembleDebug, Gradle fetches libraries (Compose, Room, Coroutines), compiles Kotlin files into Java bytecode, transforms them into Dalvik Executable (.dex) files, and bundles your resources.

Key File: build.gradle.kts defines dependencies and targets Android 16 (targetSdk = 36). From API 35, Android forces apps to draw edge to edge, so screens must pad themselves around the system bars.
3

The Passport: Manifest

AndroidManifest.xml is the app's official identity declaration submitted to the Android OS. If a permission, activity, service, or receiver isn't registered here, Android will crash with a SecurityException if the app attempts to run it.

Key Registrations: AppMonitorService (Accessibility), BlockOverlayActivity (Overlay), TaskDeadlineReceiver (Alarms).

The 4 Fundamental Android Building Blocks

1. Activity

The visual screen the user interacts with. FocusBank has MainActivity (dashboard/tabs) and BlockOverlayActivity (full-screen shield).

2. Service

A background worker without UI. FocusBank's AppMonitorService is an Accessibility Service that runs continuously in background memory.

3. BroadcastReceiver

A radio receiver for OS-wide broadcasts. Listens for phone reboots (BOOT_COMPLETED) or screen sleep (SCREEN_OFF).

4. ContentProvider

Securely shares structured data between apps or provides underlying storage abstraction (FocusBank relies on Room SQLite directly).

Modern Declarative UI: Jetpack Compose

In older Android development, developers wrote rigid XML layout files and manually found views with findViewById(). In Jetpack Compose, UI is defined as pure Kotlin functions that automatically redraw ("recompose") whenever underlying state variables change.

The Secret: State & Recomposition

Compose UI is a function of State: UI = f(State).

  • remember { mutableStateOf(120L) } creates an observable state variable.
  • When the background ticker decrements balance from 120s to 119s, Compose recalculates only the text element displaying the seconds.
  • No manual textView.setText() calls required!

SharedPreferences & Cache

Microsecond Reads

Used for high-frequency settings: balance_seconds, blocked_apps, and active penalty timers.

The Problem: Every tick read today's usage row from SQLite before writing it back.

The Fix (v1.2): An in-memory usageCache keeps the running count so the per-second read is skipped. It lives in a companion object because the service builds a new FocusBankStore every second; in 1.1 the cache belonged to each instance and was always empty.

v1.3: allowMainThreadQueries() is gone. The UI reads Room on Dispatchers.IO, receivers use goAsync(), and the accessibility service works on its own HandlerThread. A lock keeps balance updates from racing between threads.
v1.6: the database grew a column

Plans added isPlan to the tasks table. Room is now at schema version 2, with a MIGRATION_1_2 that runs ALTER TABLE … ADD COLUMN isPlan INTEGER NOT NULL DEFAULT 0 once on existing installs. All reads run off the main thread. See tab 10, lessons 1 and 3.

The Background Guardian: Accessibility Service

How can FocusBank know when you opened Instagram or Chrome if FocusBank isn't on your screen? Modern Android does not allow background apps to spy on running apps—unless they run an authorized AccessibilityService.

Since v1.4: the service only forwards events. Every decision (charge, block, penalty) lives in EnforcementEngine, driven by one 1-second tick() on a background thread. See tab 10, lessons 1 and 2.
1. OS Event Callback

onAccessibilityEvent()

Whenever a window transitions (typeWindowStateChanged), Android sends the foreground package name (e.g. com.android.chrome) to FocusBank.

2. Intelligent Filter

isIgnoredPackage()

When you type, Gboard or Samsung Keyboard takes focus. FocusBank detects and ignores keyboard popups and System UI so it doesn't falsely reset your timer!

3. Power & Lock Guard

Keyguard & Screen Off

If your phone screen goes to sleep (SCREEN_OFF) or the lockscreen is active, FocusBank freezes the ticker so you don't lose time in your pocket!

Android 14 (API 34) Foreground Compliance:

On Android 14, calling startForeground() without a declared Foreground Service Type throws MissingForegroundServiceTypeException. FocusBank declares FOREGROUND_SERVICE_TYPE_SPECIAL_USE and shows an ongoing low-priority notification. This makes the process much less likely to be killed, but it is not a guarantee: some OEM battery managers still stop it, which is why the UI checks a service heartbeat.

Real-World Case Study Hardware Debugging

The Mystery of the Missing Seconds (And How We Solved It)

During physical device testing on a Vivo phone running Android 14, an elusive bug appeared: users used WhatsApp and Chrome for over an hour, but the timer stopped counting after a few seconds! Here are the major loopholes discovered and fixed. The 4th was found in the v1.2 spec audit:

1. The OEM Gesture Trap

Swiping on Vivo phones fires events from com.vivo.upslide. FocusBank thought the user exited the app and killed the ticker!

Fix: Filter all OEM services in isIgnoredPackage().
2. The Back-Button Bypass

When balance hit 0, pressing the phone's Back button closed the overlay and let the user right back into Chrome with a dead timer!

Fix: Intercept Back button and force-route to CATEGORY_HOME.
3. Dropped OS Events

If the ticker died, no new window events fired while scrolling inside the same app, leaving the timer permanently frozen.

Fix: 1-second continuous background Watchdog pulse.
4. The Silent Hand-off

If the ticker itself noticed you jump from Chrome straight into WhatsApp, it called startAllowanceTicker(), which returned early because the ticker was "already running". Nothing rescheduled it, and the watchdog trusted the stale flag, so WhatsApp ran free.

Fix (v1.2): clear the flag and run the full handlePackageEvent() check.

From Laptop to Pocket: The Build Pipeline

How source code transforms into a runnable app on your physical Vivo phone.

1

Kotlin Compilation & Desugaring

Gradle invokes kotlinc. Modern Java 17 features are "desugared" so they run seamlessly even on older Android operating systems down to Android 8 (API 26).

2

Dexing & Packaging (assembleDebug)

The D8 compiler turns bytecode into Dalvik Executables (classes.dex). Resources, icons, and compiled XML files are compressed into app-debug.apk.

3

ADB Streamed Install

The Android Debug Bridge streams APK bytes over USB directly into the phone's package manager daemon (/system/bin/pm), which verifies signatures and registers the app.

4

Next Step: Google Play Store Release (AAB)

For Google Play, we run ./gradlew bundleRelease to output an Android App Bundle (.aab) signed with your private cryptographic keystore. Google Play then dynamically generates optimized mini-APKs for each user's specific screen size and CPU.

5

Today's toolchain and the release signing

FocusBank builds with AGP 8.9.1, Gradle 8.11.1 and Kotlin 1.9, compiling against and targeting API 36. Release builds read your upload key from keystore.properties. Without it they come out unsigned, with a warning. Keystores and the full Play route are in tab 11.

Study guide · v1.2 → v1.6

Engineering Lessons from Building FocusBank

Eight lessons, each tied to a real bug or decision in this codebase. Read them in order: each builds on the one before.

1. One main thread, and nothing slow on it

Android draws the screen and handles taps on a single main thread. Anything slow there, like a database query, freezes the UI, and after about 5 seconds Android shows "App isn't responding". Room enforces this by throwing if you query on the main thread, unless you call allowMainThreadQueries(). FocusBank 1.2 did exactly that, and 1.3 removed it.

Each entry point hands database work to its own background route; the store is shared.

The new problem: two threads, one balance

Once the service ticked on its own thread, two writers could collide. The UI reads the balance (100), adds a 20-minute reward and writes 1300. Meanwhile the service reads 100, subtracts 1 second and writes 99. The reward is lost. This is a read-modify-write race.

The fix: every balance, reroll and penalty update runs inside synchronized(LOCK) { … }, so only one thread can be in the middle of an update.

Rule of thumb
  • UI → scope.launch { withContext(Dispatchers.IO) { … } }
  • Receivers → goAsync() keeps the process alive while a thread works
  • Long-lived services → a HandlerThread that owns all their state
  • Shared mutable data → one lock, or one owning thread

2. Make the rules testable by pushing Android to the edge

The blocking rules used to live inside AppMonitorService, mixed with calls only a real phone can make. You can't unit-test that. Version 1.4 moved every decision into EnforcementEngine, which talks to the phone only through a small interface, EnforcementHost. The real service implements it on the phone, and a FakePhone implements it in tests.

Pure rules → plain JUnit

TaskRules has no Android code, so rewardSeconds(), dailyUnlock() and the others test in milliseconds on your laptop.

Android pieces → Robolectric

Robolectric simulates SharedPreferences, Room (in memory), alarms and notifications on the JVM, so the store and receivers run without a phone.

Test your tests (mutation)

Break a rule on purpose and check that a test fails. Breaking the old Chrome → WhatsApp hand-off made a test fail, so that bug can't come back unnoticed.

The 11 pm lesson: one test said "a task due in 1 hour blocks today's unlock". It passed all day and failed at 11:12 pm, because 1 hour later was tomorrow. Tests that read the real clock must pick times that hold at any hour, or take the clock as a parameter.

3. Changing a database that already has your data

Plans needed a new isPlan column, but your phone already had a version 1 database with real tasks. Room stores a schema version. When the code says version 2, Room runs your migration once and then checks that the result matches the new entity exactly. Without a migration, the app crashes, or it wipes the data if you allowed destructive migration.

// FocusBankDatabase.kt
@ColumnInfo(defaultValue = "0") val isPlan: Boolean = false
val MIGRATION_1_2 = object : Migration(1, 2) {
override fun migrate(db: SupportSQLiteDatabase) {
db.execSQL("ALTER TABLE tasks ADD COLUMN isPlan INTEGER NOT NULL DEFAULT 0")
}
}
  • The SQL DEFAULT 0 and the entity's defaultValue = "0" must agree, or Room's schema check fails at startup.
  • The test builds a database with the exact v1 SQL Room generated (copied from FocusBankDatabase_Impl), runs the migration and reads the old task back.
  • On your phone: PRAGMA user_version went from 1 to 2, and your task survived as a commitment.
  • Never edit a migration that has shipped. Add a new one (2 → 3) instead.

5. Accessibility is powerful, so everyone distrusts it

An Accessibility service can see which app is open, and with canRetrieveWindowContent it can read what's on screen. Banking malware abuses exactly this, so the rest of the system defends against it:

Google Play

Apps that aren't assistive tools need a prominent in-app disclosure plus explicit consent before the user enables the service, and a declaration in the Play Console.

UPI and banking apps

Many refuse payments while an untrusted service is on. Each app's rule is secret. Some check what the service can see, others whether any service is on at all.

Android itself

A service may switch itself off (disableSelf()) but never back on. Turning it on always needs the user in Settings.

The FocusBank decision: an in-app off switch would make dodging the blocker one tap away. So the Vault explains the Settings route for UPI payments instead, and "Enable blocking" deep-links back. The friction is the feature.

6. Designing rules people can't easily game

Ask: "how would I cheat this?"
  • Plans pay nothing, or they would become a minute printer.
  • A task's type is fixed at creation, so a missed commitment can't become a plan.
  • A penalized app's protection can't be switched off.
  • A reset can't mint a second daily allowance.
  • Still open: one trivial commitment unlocks the day unless a screen-free goal is set.

7. Pin down a requirement with an example before you build it

"The penalty should only be consumed when there is time in the vault" was first built as "counts down only while you spend Vault time in another app". The intended rule was simpler: "counts down in real time while the Vault is above 0". Both readings were plausible. A concrete example would have caught the mismatch before any code was written:

"Vault 60 min, 20 min penalty on Instagram, phone idle for 20 min. Is Instagram free again?" Intended: yes. First build: no.

The cost was one extra version (1.4 → the fix) and the tests rewritten twice. Worked examples in the spec are cheaper than rework.

8. Git as a safety net

  • Commit = checkpoint. Every version (1.2 → 1.6) is one commit you can return to.
  • Branch for work in progress, then merge into main. A fast-forward merge keeps history a straight line.
  • .gitignore secrets first: *.jks, keystore.properties, local.properties.

Study guide · signing & release

Keystores and Publishing to Google Play

Part A explains app signing from scratch. Part B walks the Play Store route step by step, with what it costs and how long it takes. Play's rules change, so confirm numbers in the Play Console before you rely on them (written October 2026).

Part A · What a keystore is

Every APK is signed with a private key. Android installs an update only if it carries the same signature as the installed app, which is how your phone knows the update came from the same developer. A keystore is the password-protected file (.jks) holding that private key and its certificate.

Keystore file

The .jks container, protected by the store password.

Alias

The name of one key inside it, e.g. focusbank-upload.

Key password

Protects that key; usually the same as the store password.

Certificate

The public half: your name, organisation and country, plus validity (10000 days ≈ 27 years).

Debug key vs release key

Android Studio and Gradle sign debug builds automatically with ~/.android/debug.keystore (password android), which is the same on every developer's laptop. That's fine for testing and never accepted by Play. Practical consequence for you: FocusBank on your phone is debug-signed, so a Play or release-signed version can't install over it. You'd have to uninstall first, which deletes its data. Export a backup before switching.

Play App Signing: two keys, not one

New apps on Play must use App Bundles and Play App Signing, so your keystore is the upload key. Losing it is painful but recoverable. Without Play App Signing, for example if you only ever share APKs yourself, losing the key means no one can ever update the app. Back it up.

Signature schemes

SchemeNeeded fromNotes
v1 (JAR)all versionsOnly matters below Android 7. FocusBank's minSdk is 26, so Gradle skips it.
v2Android 7 (API 24)Signs the whole APK; what FocusBank's release APK uses

Doing it for FocusBank

  1. Create the key (once):
    mkdir -p ~/keys
    keytool -genkeypair -v -keystore ~/keys/focusbank-upload.jks -alias focusbank-upload -keyalg RSA -keysize 4096 -validity 10000
  2. Inspect it any time: keytool -list -v -keystore ~/keys/focusbank-upload.jks shows the alias, validity and SHA-256 fingerprint.
  3. Copy keystore.properties.example → keystore.properties and fill in the path and passwords. The file is git-ignored.
  4. ./gradlew bundleRelease → app/build/outputs/bundle/release/app-release.aab. No "UNSIGNED" warning means it's signed.
  5. Back up the .jks file and passwords outside this laptop, in a password manager or on an encrypted drive.

How updates work: Android's three rules

Android installs a new APK over an existing one, keeping its data, only when all three hold:

  1. Same package name: com.focusbank.app. Never change it.
  2. Same signing key: the certificate must match the installed app's.
  3. Higher versionCode: an integer in app/build.gradle.kts (now 10). versionName ("1.7.0") is only a label people see.
InstalledInstallingResultWhat to do
Release 1.7.0 (code 10)Release 1.8.0 (code 11), same keyUpdates, data keptNothing, this is the normal path

Release, code 10Release, code 10 or lowerRefused: not newerAlways raise versionCode

A website can't push updates. People only get a new version when they download it again. An in-app "new version available" check would need the INTERNET permission, which would break the "no internet access" privacy promise. That's a real trade-off to weigh, not a free feature.

When FocusBank moves to Google Play

Play App Signing asks which key it should sign users' downloads with. That choice decides whether people who installed from the website can update from Play:

Give Play your existing key (recommended once you have users)

Upload focusbank-upload as the app signing key using the export tool the Console provides, then create a new, separate upload key. Play versions then install over website versions, and nobody loses data.

Let Google generate a new key

Simpler, but Play and website builds are then signed differently. Website users must back up, uninstall and reinstall from Play.

The Console's exact wording changes over time; look for the app-signing key option during setup.

If something goes wrong with the key

  • Lost, website only: no update can ever install over the existing app again. Everyone would have to uninstall and reinstall a newly signed app. Keep two backups of the .jks and the password.
  • Lost, Play with Play App Signing: Google holds the signing key, so Play support can reset your upload key.
  • Leaked: rotate to a new key with APK Signature Scheme v3 (apksigner rotate). Android 9+ devices accept updates signed with the new key, but rotating needs the old key, which is one more reason never to lose it.
  • Never commit it: *.jks and keystore.properties are in .gitignore, and the public website repository contains only the website.

FocusBank: everything you need to talk about this project

An overview of FocusBank: what it does, how it is built and tested, and its limitations. Every number on this page matches the code as of version 1.7.0.

A. The pitch

30 seconds

"FocusBank is an Android app that makes screen time something you earn. Distracting apps are locked by default; finishing tasks on time adds minutes to a Vault, and using a protected app spends them. Miss a deadline and a random protected app gets locked as a penalty. It's built in Kotlin with Jetpack Compose and Room, and enforces the rules with an Accessibility service. It's fully offline, targets Android 16, and has 89 automated tests."

2 minutes: problem → solution → hard parts → result

Problem. Screen-time limits are easy to dismiss because they're a fixed allowance you never earned. I wanted the incentive reversed: time is a reward for finished work.

Solution. Tasks carry a reward and a penalty. A Vault balance grows when you finish on time (plus 30 free minutes a day) and shrinks second by second while a protected app is open. An Accessibility service watches which app is in front and shows a full-screen block when the Vault is empty, a penalty is active, or the app's own daily limit is used up.

Hard parts. Reliable foreground detection on a Vivo phone that drops events and fires OEM gesture events. Keeping the database off the main thread once enforcement moved to its own thread, which created a race on the balance that I fixed with a lock. Making the blocking rules unit-testable by extracting them from the Android service. Migrating the database without losing users' tasks. Meeting Play policy for Accessibility use.

Result. Version 1.7.0: 13 Kotlin source files (about 2,900 lines), 89 tests across 5 test classes, running on a real device. It's distributed as a signed APK from its own website (dasa108.github.io/focusbank) while the Play Store release waits.

E. The rules, exactly

  • Vault: a balance in seconds. +30 min once a day, plus an optional extra 30 min at a time you choose.
  • Spending: 1 second per second while a protected app is in front. Pauses when the screen is off or locked.
  • Commitment: reward only if finished by the deadline; 24 h early also earns a reroll. Missing it locks a random protected app for its penalty minutes, unless a reroll absorbs it.
  • Penalty: counts down in real time while the Vault is above 0 and pauses at 0. It never costs Vault time. When it ends, the task is rechecked, and if still open a new penalty is rolled.
  • Plan: reminder only. No reward, penalty or reroll, and it never affects the unlock.
  • Daily unlock: every commitment due today or overdue is done, at least one was finished today, and the screen-free goal (if set) is met. Protected apps then open even with an empty Vault.
  • Per-app time limit: a cap on top of the Vault. Each second costs Vault time and limit time; whichever runs out first blocks the app. It holds on unlock days and refills at midnight.
  • Screen-free goal: minutes with the screen off, counted only after the day's first screen-on.

F. Five debugging stories (Situation · Task · Action · Result)

1. The missing seconds
S: On a Vivo phone the timer stopped after a few seconds of WhatsApp. T: Find why tracking ended. A: Logged every window event and found swipe gestures arriving from com.vivo.upslide, which was treated as "user left the app". Ignored OEM helper packages and added a 1-second watchdog for dropped events. R: Continuous tracking on the device.
2. The silent hand-off
S: Jumping from Chrome straight into WhatsApp left WhatsApp uncharged. T: Find the hole. A: Traced two Handler loops: an early-return guard saw "ticker already running", so the runnable never re-posted. Routed the switch through the full check, then rebuilt everything as one tick in a testable engine. R: A regression test that fails if the bug comes back, proven by deliberately reintroducing it.
3. The lost reward
S: After moving enforcement to a background thread, rewards could vanish. T: Explain and fix. A: Identified a read-modify-write race between the UI adding a reward and the service subtracting a second. Wrapped every balance, reroll and penalty update in one lock. R: Correct totals under concurrency.
4. The 11 pm test failure
S: A test passed all day and failed at 11:12 pm. T: Find the flakiness. A: It assumed "due in 1 hour" meant today; after 11 pm it's tomorrow, which the new unlock rule correctly ignores. Rewrote it with an already-due task and added an end-of-day helper with its own test. R: Time-independent tests.
5. The misunderstood requirement
S: "Penalty only consumed when there is time in the vault" was built as "only while spending Vault time elsewhere". T: Align with the owner. A: Asked with a concrete example, reverted to "counts down while the Vault is above 0", kept the new tests, and since then confirm edge cases with worked examples first (as for time limits on unlock days). R: One wasted version, and a lasting process change.

G. How I know it works

  • Unit tests on pure rules (TaskRules) run in milliseconds.
  • Robolectric tests on the store (in-memory Room), receivers and alarms, and on the engine through a FakePhone with a scripted screen and clock.
  • A migration test builds a database with the exact version 1 schema Room generated and upgrades it.
  • Mutation checks: deliberately break a rule and confirm a test fails. Done for the hand-off, the penalty rule and the time-limit cap.
  • On the device without touching the UI: adb logcat for crashes, run-as … sqlite3 for the schema version and data, dumpsys for notifications and the focused window, and a service heartbeat timestamp.
  • Android lint caught a real API-level bug (a foreground-service type passed on Android 10–13).

H. Honest limitations and what I'd do next

  • It runs on an honour system: you set your own rewards and can turn Accessibility off in Settings. It's a self-control tool, not parental control.
  • No ViewModel yet: screen state lives in composables and refreshes from a 1-second loop. Next step: ViewModel + StateFlow, and Room Flow queries for reactive updates (the ViewModel library is already a dependency).
  • SharedPreferences + a lock for frequently changing values. DataStore or Room transactions would be sturdier.
  • kapt → KSP and R8 shrinking are still to do. Alarms are inexact. Battery use hasn't been profiled.
  • The Android shell (AppMonitorService) is only tested on one physical device, so other brands need a closed test.
  • Not on Google Play yet. It ships as a signed APK from a GitHub Pages site, so there are no automatic updates: users download each new version themselves (tab 11, Part B).

Tab 13 · Choices

Why these libraries and tools, and not the others

"Why did you use X?" is the most common follow-up question in a project interview. This tab covers every library and tool in FocusBank: what each was chosen over, why, and what the choice cost. Tab 12 has the short version of the stack; this is the long one.

A formula for any "why X over Y?" answer
  1. The constraint: what the app needed, such as offline use, reacting within a second, or Play policy.
  2. The options: two or three real alternatives, so you show you knew there was a choice.
  3. The choice and its cost: what you picked and what you gave up. Naming the cost is what makes the answer believable.

Example: "Blocking had to react the instant an app opened. UsageStatsManager only reports after the fact, and a VPN only blocks network traffic. So I used an Accessibility service. The cost is that it's a high-trust permission, so I had to add a consent screen, and some UPI apps refuse to pay while it's on."

The constraints behind every choice

Most of the decisions below follow from these six facts. If you forget a detail in an interview, reason from them.

Android only. Blocking other apps is impossible on iOS outside Apple's Screen Time framework, so there was no reason to go cross-platform.
Offline, no internet permission. This rules out every cloud database, analytics SDK and in-app update check.
Reacts within a second. This needs live events plus a 1-second tick. Anything deferrable or delayed is out.
Built by one developer. Every library has to justify the setup and upkeep it adds. Fewer moving parts wins.
Play policy. Accessibility consent, no QUERY_ALL_PACKAGES, no exact-alarm permission, target API 36.
No money. Hosting, distribution and tools must be free, so no Play fee for now.

The choices I'd revisit, in order

Saying what you'd change shows you understand the trade-offs, not just the tools.

  1. ViewModel + StateFlow + Room Flow instead of state in composables: survives rotation and updates reactively.
  2. KSP instead of kapt: faster builds; kapt is in maintenance mode.
  3. DataStore for settings while keeping a synchronous, locked store for the per-second ledger. Not everything has to move.
